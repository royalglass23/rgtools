# Work Orders evidence assessment

The signed-in dashboard refresh action reconciles ServiceM8 first, then runs `refreshDueAssessments` under the existing shared refresh lease. Visible auto-refresh uses the same action. Page reads only recompute the Auckland today-through-21-days window; they do not call AI. Existing Production Specification enrichment is a separate workflow.

## Rules and source

Read-only inspection of the [Kanban bot](https://grok.com/bot/e53f85c3-1944-43c3-b3f9-260c5c9c0c88) and its saved Daily RG Kanban refresh routine found vendor verification, preservation of manual values and a ban on using bookings as installation dates. The delegated [build_kanban.py](https://drive.google.com/file/d/1xxW_fDCIHX_D2h3tanBJsqCwrUZg8JoM/view) consumes curated evidence and spreadsheet flags; it is not itself a runtime AI detector. Its explicit Y/N/? priority is preserved here. Sheet/PDF rebuilds, uploads, messaging and related-job writes are outside this implementation.

`modules/kanban/assessment-source.ts` reads complete bounded active note/email cursor slices, reconciled job/item descriptions and a fresh job GET for allowlisted top-level custom-field text using the GET-only wrapper. Source failure, cursor loops, source identity/description changes or oversized history fail closed. There is no calendar/task input. Known client/address, contact, price, link and obvious secret text is redacted before provider input. Known configured installer names/IDs become opaque installer tokens; product/source tokens replace record IDs. Source text remains untrusted data.

`assessment-provider.ts` uses the existing backend `OPENAI_API_KEY`, optional `KANBAN_ASSESSMENT_MODEL` (otherwise `OPENAI_MODEL`, then `gpt-5.4-mini`) and Responses structured output with provider storage disabled. Exact quotes, known product/source tokens, dates, purpose and product scope are validated locally. Uncertain scope, unsupported year, cancellation or booking intent requires review. Relative wording is anchored to the source timestamp, never today's retrieval time. Results remain AI suggestions and cannot confirm dates or modify staff fields.

The operational v1 response is keyed by exact product tokens, with a date envelope and every required operational field per product. The server restores item IDs, verifies exact known source/installer tokens and applies field-specific meaning, product scope, supported date and newer-conflict checks. Structural completeness is required; an unsupported individual claim becomes review with no accepted value. The format follows [OpenAI structured-output schemas](https://developers.openai.com/api/docs/guides/structured-outputs); local semantic validation remains mandatory. Old date-only stored payloads stay readable and are reassessed on the new rules/schema fingerprint.
Complete evidence is bounded to 160,000 characters and 900 sources, with existing per-record and pagination limits retained. The previous 60,000-character cap rejected six current job histories before AI. Raising the bound keeps those histories complete; no dates or later cancellations are silently truncated. The configured provider passed a synthetic nine-product, 128,442-character case after repair. Historical failed assessments remain failed until a normal refresh retries them under the new rules.

## Imported Master flags

`kanban.master-flags.v1` is a dedicated JSON settings value holding source-provenance-bearing job flags; it requires no new migration. The source Sheet stays read-only. Each entry is bound to the RG Tools job ID, ServiceM8 job UUID and job number. Product choices have highest priority, then imported Master Y/N/?, then the automatic date rule. Y can retain TBC/overdue work even when AI fails. Imported flags never change dates, readiness, notes, installers or product revisions. A product reset to automatic inherits its job flag again; new products inherit it too.

The current approved transfer is a one-time snapshot, not continuous Google Sheets synchronisation. Read the live Master Job No/Status and Within 3 weeks? columns, retain source sheet ID/cell/modified time in a private manifest, and use the CLI from the repository root:

```powershell
node node_modules/tsx/dist/cli.mjs --tsconfig apps/web/tsconfig.json apps/web/scripts/kanban-flags.ts --target prod --input tmp/rg406/kanban-master-flags.json --output tmp/rg406/kanban-master-import-plan.json
node node_modules/tsx/dist/cli.mjs --tsconfig apps/web/tsconfig.json apps/web/scripts/kanban-flags.ts --target prod --input tmp/rg406/kanban-master-flags.json --apply --expected-plan "PLAN_HASH_FROM_PREVIEW"
```

Preview is read-only. Apply checks the exact preview fingerprint, locks current job identities and the settings row, rejects unmatched/ambiguous/stale plans, and writes only the dedicated setting and `dashboard_kanban_flag_imported` job events under the shared refresh lease. Unchanged re-imports do not create events. Events are visible from each product's history. A CLI import uses the System actor and records staff-requested provenance rather than impersonating a staff account. Existing entries outside the manifest are retained for archived jobs. Use `--target local` with the named disposable database for tests. Keep manifests/previews out of Git.

## Storage, refresh and failure

Rule version `kanban-operational-v3-20261118` retains the bounded date grammar: day/month dates without a year require a trustworthy note/email timestamp and a unique date within 90 days. December/January rollover and associated weekdays are checked. Descriptions/custom fields have no trustworthy field-authoring timestamp; neither retrieval time nor generic whole-job edit_date can anchor their relative/yearless dates. Unsupported dates, questions, conditional plans and unclear job-level scope remain reviewable. Applicable conflicting/cancelled evidence also requires review. The rule bump invalidates older cached decisions; the operational JSON schema remains v1.

Client waiting for is a narrative summary of sourced outstanding work or requests. It accepts expectations and unresolved questions without requiring literal waiting-for wording or a verbatim summary. Exact source quotes, product scope, negative/closed wording checks and staff ownership remain enforced. This summary exception does not relax readiness, issuance, consent or planning-date validation; questions still cannot prove those states.

Evidence presentation preserves timestamp precision: a date-only source stays date-only, while supported timezone-less note/email timestamps display in the contracted Royal Glass Auckland account context. Explicit offsets retain their instant, and missing/invalid/other-source authoring remains unknown. ServiceM8 documents ordinary timestamps as account-local and webhooks as the UTC exception in its [webhook overview](https://developer.servicem8.com/docs/webhooks-overview). This UI formatting does not change backend temporal assessment rules.

Assessment failures appear above the tables even when the due view is empty. Subsequent failure records distinguish source preparation, provider timeout/request, output validation and persistence using fixed safe messages; raw provider errors and source text are never used as error messages. Older failed records retain their generic message until retried. A dated suggestion is still unconfirmed and never overwrites a staff target.

Migration **0073** adds `work_order_items.dashboard_assessment` JSONB, separate from canonical `install_date` and `dashboard_state`. The operational payload extends that existing JSON compatibly; checkpoint 2 adds no schema migration or live backfill. Apply existing required migrations through the normal reviewed release process before deployment.

Each product stores source/snapshot hashes, rule/model versions, checked/assessment times, date result, optional versioned operational results, coverage and error. The fingerprint includes selected evidence and authoring timestamps, product inventory, source policy/coverage and active installer inventory. Fetch time and staff-only edits do not cause provider churn; note/email/custom-field or installer-list changes do. Refresh now captures durable run/work items after one complete source reconciliation. Bounded authenticated continuation requests assess remaining jobs without repeating that full sync. Saved work survives navigation/process restart; visible signed-in tabs resume it, while hidden/closed tabs schedule no further batches. Progress keeps source-sync time separate from terminal assessment completion. Jobs with no eligible product remain visibly unavailable. Assessment-only transactions recheck current source identity, description, product inventory, source-sync generation, installer snapshot and the previously observed stored assessment before saving. A late result cannot overwrite a newer committed assessment. These are local checks, not a distributed lock on remote ServiceM8 edits. Meaningful changes create actor-attributed `dashboard_evidence_assessed` events; unchanged cache checks do not spam history.

Staff-owned dates, including deliberate null clears, take priority over suggested dates. A suggested date can drive the effective value only when that field uses automatic assessment. Product Include/Exclude/Needs review controls determine membership before imported Master flags and automatic rules. Assessment storage never changes those values or their revision. A suggestion is usable only when complete, on the current rules, matching the current source descriptions and checked after the latest successful source sync. Failed or stale results remain visible for review and cannot classify an automatic date row; explicit flags still apply. Missing configuration, incomplete access and pending/failed work are surfaced in refresh feedback. Invalid saved flag data fails closed for inherited automatic choices and produces a visible banner; product overrides still apply.

## Durable assessment runs

Migration **0074** adds `work_order_assessment_runs` and `work_order_assessment_work`, separate from source-refresh history. The run captures source snapshot/generation, schema/rules/model/source-policy versions, requesting account, immutable inventory denominator and durable progress. Per-job work holds attempts, availability, lease token/expiry, executing account and terminal outcome. Captured job identity is retained even when a source job is deleted; source deletion cannot cascade away pending work or its counts.

Start, status and continuation actions recheck the signed-in stored account and existing all-staff dashboard boundary, validate inputs and apply rate limits. Actual executors are attributed to their own assessment events rather than impersonating the original requester. Full source refresh and assessment batches share the existing refresh lease. Source/provider deadlines and bounded concurrency keep each request finite, and started siblings settle before lease release.

Atomic claims recover expired leases. Publication checks the exact live claim and active run in the same transaction that writes assessment/history; source/product/installer/prior-assessment CAS remains required. A stale token or superseded run cannot publish even if its captured source generation still matches. Failures retry only to the configured ceiling and then need staff retry; completion requires every captured item to be terminal. A changed observed source or rules/model snapshot can supersede older work. Staff overrides and observation/fetch time alone do not create provider churn.

The client performs bounded visible-tab status/continuation polling with backoff. Unsaved drafts pause new full refreshes and batches; in-flight safe assessment writes may finish without refreshing dirty editors. Hidden/unmounted tabs cancel further scheduling. The periodic source timer resumes an active run instead of continually replacing it; retry-exhausted runs wait for an explicit staff refresh. This is signed-in browser continuation, not an unattended queue worker or remote ServiceM8 transaction lock. Per-field effective values and evidence are projected by the checkpoint4 read model without changing provider/run semantics.

## Per-field staff ownership

RG-407 checkpoint 1 adds versioned per-field automatic/staff ownership in existing dashboard JSON storage. Actual stored legacy keys remain protected, including blank text, Unknown, N/A and null dates. Legacy canonical date/installer values and ambiguous nulls are protected conservatively; newly created source products begin automatic. Once versioned ownership exists it is authoritative, so normalization cannot restore an override that staff explicitly released. No bulk live backfill is required for this compatibility reader.

Dashboard saves submit only explicit changed-field/mode patches. Staff selection/clear establishes ownership even when the raw value is unchanged. The dashboard and existing Work Orders installer/date writer maintain the same metadata, revision and audit transaction. A per-field return to automatic releases only that field; for canonical target date/installer it clears the saved manual column to null, preserving the old value in history. Automatic output remains in assessment storage and never assigns an installer or confirms a date. Staff Notes are not generated assessment text.

Optimistic revision and expected canonical-value checks reject stale edits; in-flight assessment/source updates cannot replace staff drafts. The provider now stores separate operational assessments, while staff ownership remains authoritative. An older reader that ignores protected clears is not a safe rollback without a reviewed compatibility path.

## Operational fields and source coverage

Operational schema v1 covers site/glass/hardware readiness and actual versus expected dates, design confirmation, PS1/PS3 required versus issued, bottle strut, literal consent status and a separate consent identifier, minor variation, waiting-for, materials ETA, aftercare, explicit configured-installer suggestions and explicit labour estimates. Installation/delivery purpose and dates retain their separate compatible date envelope. Generated summary/gaps are separate from staff Notes. No automatic result writes manual state, ownership or canonical date/installer columns.

Every field records a validated value or unknown/review/unsupported coverage, supporting quotes and source timestamps. Ordered or elapsed ETA is not readiness; quote acceptance is not design approval; fees are not issuance; PS1 does not imply minor variation; actual time is not a labour estimate. Consent requirement/number alone is not approval. BC display follows the current Kanban builder process: pass literal resolved status text, use ? when unknown, and show the separately extracted consent reference read-only. Validated automatic approved/pending/declined is never converted to staff Y/N; existing staff Y/N/Unknown/N/A remains verbatim. No historical bot CSV values are imported. Installer suggestions do not assign staff or invent inactive/ambiguous matches.

Semantic grammar is deliberately bounded: supported English declarations and narrow Chinese glass-arrival/readiness and PS requirement/issuance phrases are checked directly. For example, 玻璃已到货 is distinct from 玻璃已下单, and 需要PS1 is distinct from PS1已签发. Negation, questions, instructions and uncertain wording cannot be removed by citing a shorter positive substring. Unknown broader wording/languages stays for review; no generic translation engine or complete language coverage is claimed. Product-local clauses also prevent evidence for one product from establishing another product's field.

Coverage distinguishes selected text reads, missing allowed custom fields and unsupported document/photo/form bodies. No image interpretation, OCR or arbitrary binary download is added. Complete selected text slices are not complete Diary history. Existing custom values are top-level customfield_ properties on the [Job REST record](https://developer.servicem8.com/reference/getjobs), as described in [ServiceM8 custom fields](https://developer.servicem8.com/docs/custom-fields-overview); this workflow does not manage custom-field definitions or change credentials.

Checkpoint 2 supplies the backend assessment/storage foundation; checkpoint 3 adds durable one-click orchestration and minimal progress/pause/retry feedback; checkpoint 4 projects effective values and per-field evidence into the incumbent tables/editor. Pending/retry feedback must not be represented as all work complete.

## Effective values and evidence UI

One shared typed projection supplies table and editor values. The default field display shows the value and a closed Details control; origin, assessment state and coverage diagnostics appear only after opening Details. Protected staff ownership, including blank/Unknown/N/A and legacy choices, wins over automatic values. Only current validated assessment facets can supply automatic values; missing/pending/stale/failed/review/unsupported cases cannot promote an old value. Last-good evidence remains inspectable as history. Supported readiness state/date/purpose are one ownership unit; dates retain actual-ready versus expected meaning. Consent status and reference, installer suggestion and canonical assignment, and generated summary/gaps and staff Notes remain separate.

Inputs and per-field mode controls submit only changed patches. Displaying automatic values never hydrates them into a whole manual snapshot. A staff Notes save cannot freeze untouched suggestions. Delivery dates are labelled with delivery purpose and cannot become a canonical installation target through a generic mode switch. Returning a canonical date/installer field to automatic retains the existing audited clear/revision checks.

Dirty editors hold their original base revision, expected canonical values, explicit local staff values and modes. Latest assessment/currentness metadata updates untouched automatic fields even while another field is dirty; stale/failed automatic values cannot remain labelled current or be silently pinned by Keep staff value. Field controls capture the currently shown value/date purpose when staff explicitly take ownership. This does not rebase canonical expectations or save untouched fields. ProductDrafts retains recoverable values/modes when filtering or source removal unmounts a row; per-product retained markers continue pausing refresh/continuation and preserve exceptProductId semantics. An explicit per-draft discard after copying releases an unmounted draft only; a live mounted editor must use its existing Save/Reload controls, and other drafts stay protected. The tab-local lifetime remains unchanged. Server assessment progress never forces a dirty editor refresh or remount, and a late status response cannot replace dirty-pause feedback. Search/page-size forms use client navigation, with committed query/size controls resynchronised without remounting the draft provider. Coverage and evidence controls stay keyboard accessible within the existing dense layout and semantic theme tokens.

Evidence timestamp presentation preserves source precision. Date-only evidence stays date-only; supported timezone-less note/email authoring time stays the account's Auckland wall time. [ServiceM8 documents](https://developer.servicem8.com/docs/webhooks-overview) ordinary timestamps as account-local and webhooks as the UTC exception. Explicit offsets retain conversion, and missing, invalid or unsupported authoring times stay unknown. These are UI presentation rules; backend temporal assessment rules are unchanged.
